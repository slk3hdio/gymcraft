# GymCraft 环境 Demo 设计

本文基于当前仓库代码提出方案；除已有 `simple_mob`、`parkour_mob` 外，下列环境 ID 均为拟新增，尚未实现。

## 1. 当前基础与实现边界

- `SimpleMobEnv` 已组合 15 个动作、6 个观测组件，但奖励为零，适合作为交互沙盒。
- `ParkourMobEnv` 已有跳跃搭高、资源发放、奖励与步数限制；Python 已有表格 Q-learning 示例，应继续作为基础控制 demo。
- 菜单支持槽位观测、顺序 `moves[]`、每项 `repeat`、结果槽回调与 stale 校验，适合物品整理、合成和加工任务。
- `move_to` 使用游戏寻路，适合物流和规划任务。测量底层运动能力时只暴露 `step_move` 等动作。
- `self` 不包含背包清单；物品任务必须通过 `menu` 获取槽位信息，不能假定存在玩家式 36 格背包。需要多种资源时优先使用已有容器槽测试覆盖的村民，禁用空闲期原版 AI，并检查具体动作的控制策略。
- reset 会还原受控 Mob；场地方块、容器内容、熔炉进度、其他实体和掉落物需要环境自行恢复。现有跳搭环境的记录只覆盖部分场地修改，不能直接充当完整世界快照。
- Python 通过 gRPC 连接已创建的环境；布景与环境创建可以由 RCON 启动脚本负责，奖励和结束判定应由服务端环境负责。

## 2. Demo 总览

| 建议顺序 | 环境 ID | 任务 | 主要能力 | 新增工作量 |
|---|---|---|---|---|
| 1 | `gymcraft:sort_inventory` | 将箱内物品按指定区域整理 | 槽位规划、数组移动 | 小 |
| 2 | `gymcraft:craft_order` | 按订单合成指定数量物品 | 配方规划、连续取产出 | 中 |
| 3 | `gymcraft:waypoint_nav` | 绕过障碍，依次到达路标 | 局部观测、运动控制 | 小至中 |
| 4 | `gymcraft:smelt_order` | 分配燃料并交付加工产物 | 等待、资源预算、跨菜单记忆 | 中 |
| 5 | `gymcraft:bridge_crossing` | 使用有限方块搭桥到对岸 | 建造与运动组合 | 中至大 |

以下数值是首版建议配置，奖励系数在规则基线跑通后调整。

## 3. 箱子整理员：sort_inventory

**场景与目标**：单箱放入三种混杂物品，将前三行分别整理为石料、木料、金属。目标区域通过任务配置明确告知；要求所有原始物品仍在箱内，且各行不含错误类别。允许同类堆叠，首版保证目标容量足够。

**动作与观测**：只暴露 `open_menu`、`close_menu`、`move_menu_item`、`noop`，使用 `self`、`menu`。出生点固定在交互范围内，排除导航干扰。槽位 ID 根据当前菜单观测和布局解析，不把 GUI 索引直接当成 `slot_id`。

**关键玩法**：先从观测构建空槽和堆叠容量表，再发送一个 `moves[]` 完成多次整理。循环换位时利用空槽作为缓冲；数组中的中间槽可以被后项继续使用。数组仅限同一菜单会话，不跨箱子执行。

**奖励与结束**：正确区域中物品比例的变化乘以 5，全部整理成功额外奖励 10。移动成本按实际完成的原子移动数计费，而非仅按 RPC 次数，避免批量请求改变任务成本。正常任务失败设为终止，预算耗尽设为截断；首版预算为 128 次原子移动。

**reset 与随机化**：清空并重建箱子内容，随机种类、数量、位置及堆叠碎片；首版至少保留一个空槽。记录初始物品总量做守恒验证。后续加入无空槽但可以合并堆叠的关卡。

**基线与验收**：贪心合并、清空目标区、分批搬运的规则策略；固定测试种子全部成功，重复整理不能刷正奖励；记录成功率、原子移动数、RPC 数、错误槽位数和物品守恒情况。

## 4. 合成订单：craft_order

**场景与目标**：出生于工作台旁，初始容器提供木板，要求制作并携带 8 根木棍。进阶订单为从原木开始制作木板，再制作木棍，最后制作木镐。首版提供配方说明，把主要难点放在槽位操作与数量规划。

**动作与观测**：`open_menu`、`close_menu`、`move_menu_item`、`noop`；使用 `self`、`menu`。优先使用有容器槽的村民承载不同资源，预留产物空间。

**关键玩法**：在一个 `moves[]` 中顺序放入两格材料，再从结果槽取产物；结果槽移动使用 `repeat` 连续合成。各次结果槽取出仍执行原版配方消耗。每次换配方或菜单后，重新读取观测并解析槽位。不同组件在同一 action 中不是任意顺序脚本，打开菜单和依赖新会话 ID 的移动应分成不同 step。

**奖励与结束**：每个订单的产物净进度提供有限奖励，完成订单额外奖励 10，按原子移动计成本。产物必须进入 Agent 自有槽，停留在结果槽不计交付；移出再移回不重复得分。无法完成订单的资源状态作为任务失败；首版上限 128 次原子移动。

**reset 与随机化**：关闭旧菜单，清理残留产物与掉落，恢复原料数量，随机原料槽位和订单数量。测试种子使用不同布局，防止背槽位答案。

**基线与验收**：基于配方的规则策略；验证一条数组包含材料放入和结果取出、连续产出、空间不足时部分完成、reset 后资源守恒。

## 5. 路标导航：waypoint_nav

**场景与目标**：在约 $11\times11$ 的围墙场地内设置障碍与三个有序路标，Agent 依次进入路标半径内完成任务。首版为平地障碍，进阶增加一格台阶和窄通道。

**动作与观测**：`step_move`、`noop`，按难度开放 `jump`；不暴露 `move_to`。使用 `self`、`nearby_blocks`，任务条件提供当前目标坐标。Python 将动作离散为前后左右、转向、跳跃等有限集合，持续若干 step 的动作重复须显式计入时间和预算。

**奖励与结束**：使用到当前路标距离变化的小幅塑形奖励，首次到达每个路标奖励 2，全程完成额外奖励 10，按游戏 tick 收取时间成本。切换路标时重建距离基线，避免目标切换带来虚假奖励。首版上限 2000 游戏 tick，同时限制决策次数。

**reset 与随机化**：按 seed 生成可达布局、起点和路标；生成后做连通性检查。训练与评测分离种子，评测统计成功率、碰撞次数和实际路程。

**基线与验收**：基于局部地图的规则避障；全地图最短路径仅作为评估参考，不作为局部观测策略的输入。可复用已有 Q-learning 示例的训练循环，但状态编码与动作集合单独定义。

## 6. 熔炼订单：smelt_order

**场景与目标**：场地包含原料箱、熔炉和交付箱。初始任务把 8 个圆石烧制为石头，燃料恰好足够；进阶增加两台熔炉和不同订单数量，要求兼顾时间与燃料消耗。

**动作与观测**：`move_to`、菜单动作、`noop`；使用 `self`、`nearby_blocks`、`menu`。不开放破坏方块。各容器之间通过 Agent 自有槽运输；每次打开菜单重新观察。

**关键玩法**：装入输入和燃料，等待产物生成，再取出并交付。当前 `noop` 没有等待时长参数，可以多次 step 等待；新增带 tick 数的等待动作属于后续优化。首版可直接观察产物槽，若需要详细烧制进度，应先核实通用菜单属性是否已暴露相应字段。

**奖励与结束**：仅按交付箱的有效净交付量计进度，完成额外奖励 10，按实际游戏 tick 与已消耗燃料计成本。中途搬运、打开菜单不奖励。首版设置 4000 tick 预算，后续依据实际烧制耗时校准。

**reset 与随机化**：恢复箱内物品和熔炉完整状态，包括燃烧时间、烧制进度、配方相关状态；清除上一回合产物。随机站点位置与订单规模，确保可达且燃料可行。

**基线与验收**：单炉串行策略，再比较双炉调度策略；记录交付量、燃料消耗、游戏 tick 和决策次数。炉子会在模型思考期间继续工作，应明确这是实时世界评测；严格可复现的固定时间推进需要额外运行时支持。

## 7. 有限材料搭桥：bridge_crossing

**场景与目标**：两块平台之间有 2～4 格缺口，发放有限石块，要求 Agent 站到对岸目标区域并保持落地。进阶增加高度差和横向偏移。

**动作与观测**：`step_move`、`jump`、`set_block`、`noop`；使用 `self`、`nearby_blocks`，明确提供目标区域和剩余材料条件。不开放 `move_to`，避免掩盖移动控制能力；首版不开放 `break_block`，避免无限回收材料。

**奖励与结束**：安全地接近目标获得小幅进度奖励，成功奖励 10；掉落至失败高度终止并惩罚；按时间和方块消耗计成本。不能只用瞬时高度或距离判定成功。材料耗尽但已有通路时仍允许继续走到终点，不能直接截断。

**reset 与随机化**：恢复整个专属训练区域，既包括初始平台，也包括 Agent 放置的方块和掉落物。限制可放置坐标，防止在场外搭路绕过任务。按 seed 生成可解且预算充足的缺口。

**基线与验收**：确定性的逐块延伸桥面策略，验证 `set_block` 的距离、碰撞和消耗限制；再训练离散控制策略。记录成功率、用块数、跌落率和完成 tick。

## 8. 共用实现约定

### 服务端职责

每个环境实现 `resetMob`、奖励、终止、截断和信息输出，并通过 `EnvFactories` 注册独立工厂。首轮可以先为整理和合成共享少量场地工具，避免提前建设通用任务框架。

必须提供以下能力：

1. 专属场地边界与完整 reset：恢复方块及方块实体内容，清理本回合生成的实体和掉落物；恢复操作在服务端线程执行。
2. 由 seed 驱动的任务采样与参数校验：检查资源、容量、可达性和难度预算，非法配置在修改场景前报错。
3. 同一 step 的一致结果：当前 `AbstractMcEnv.step` 先生成 `createStepInfo`，随后才计算奖励与终止。新环境不能在奖励函数里更新状态后假定 info 已同步；应从同一时刻的快照生成不可变评估结果，统一用于所有返回字段。对世界的读写需遵循服务端线程边界。
4. 清晰终态：任务成功或失败返回 `terminated`；外部时间和步数预算耗尽返回 `truncated`。普通动作失败允许策略纠正，除非导致任务已不可完成。
5. 统一统计：任务配置、种子、成功标记、失败原因、游戏 tick、决策数、菜单原子操作数。批量移动的 RPC 数与实际移动数分开记录，并设置合理的数组及 repeat 上限，避免大请求长时间占用单个 tick。

任务条件首版可以由 reset 配置和返回 info 交给规则策略、LLM prompt。训练策略需要目标坐标、订单等条件时，Python wrapper 应明确把允许的信息加入策略观测；后续再决定是否新增通用任务观测组件。不要把用于判分的隐藏世界状态直接泄漏给策略。

### Python demo 职责

每个任务提供规则策略和运行入口，复用 `GymCraftEnv`；LLM 使用现有 `LLMGymCraftEnv`。规则基线先验证环境可解，再比较 LLM 或学习策略。客户端不重写服务端 reward、terminated 和 truncated。

建议命名为 `sort_inventory_demo.py`、`craft_order_demo.py` 等，放在 `src/main/python/demos/`。日志记录 seed、任务条件、完整轨迹和指标，避免仅记录成功视频。

### 验证顺序

先用 GameTest 验证成功、资源不足、失败中断、奖励不可重复刷取、相同 seed 布景一致及连续 reset。再启动无头服务器，经 RCON 创建环境、固定区块并运行 Python 规则策略；确保空服不暂停 tick。最后对固定未见种子评测 LLM 或学习策略。

推荐第一批实现整理与合成，集中展示新的数组移动；继续保留跳搭作为已有 RL 基线。导航补充基础控制评测，熔炼和搭桥在场地恢复工具成熟后加入。战斗任务可后续扩展，但当前附近实体观测没有目标生命值，若评估伤害控制，应先明确补充观测还是采用部分可观测任务。
